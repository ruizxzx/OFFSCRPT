# OFFSCRPT V96.0.0 — Trust, Moderation, Reviews & Marketplace Safety

## Architecture
V96 extends the existing V95 Commerce API. It does not create a second order, product, creator, or financial system. Reviews are linked to canonical V91 orders/order items; public review data is projected through the server API; moderation is stored separately from financial data.

## Collections
- `commerceReviews` — canonical review records and moderation state
- `commerceReports` — user-submitted marketplace reports
- `commerceModerationCases` — canonical moderation case per target
- `commerceModerationActions` — append-only moderation audit/action records
- `commerceTrustSignals` — safe trust-event metadata
- `commerceReviewAggregates` — server-maintained product rating aggregates

## Review lifecycle
`eligible purchase → pending → moderation/validation → published` and published reviews may move to flagged/under_review/hidden/removed. Owner edits return the review to pending. Owner removal is soft removal.

## Verification
`verifiedPurchase` is derived from the authenticated buyer, canonical Commerce order ownership, product membership, and an eligible paid/refunded order state. The browser cannot set it.

## Reporting
Reports use structured reason codes, per-user/day deterministic suppression, and a canonical moderation case per target. A report never proves a violation by itself.

## Moderation
Moderation APIs reuse the existing master-admin authorization and optionally `siteModerators` permissions. Destructive actions require structured reasons; state changes and requests are auditable.

## Trust signals
Trust is deterministic and explainable. Product publication and creator seller status remain distinct from moderation state. V96 never changes V93 allocations or V94 balances/payouts as a side effect of moderation.

## Aggregates
Only published reviews count toward product rating aggregates. Aggregate validation reports mismatches without repair. Explicit aggregate repair is available only to an authorized moderation role and is logged.

## Security
Firestore rules deny direct client access to V96 internal collections. The server is authoritative for verification, ownership, permissions, status transitions, aggregates, and audit.

## Migration / backfill
Existing products and creators continue to work without destructive migration. `scripts/backfill-v96-review-aggregates.mjs` supports bounded, idempotent, dry-run-first aggregate backfill.

## Known limitations
The first V96 implementation uses bounded Firestore reads for integrity/administrative scans. For very large datasets, production deployments should introduce cursor pagination/materialized aggregate maintenance without changing the canonical entity model.
