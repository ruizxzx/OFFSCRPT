# OFFSCRPT V93.0.0 — Commission + Profit-Cut Engine

## Purpose
V93 turns verified OFFSCRPT payments into server-authoritative marketplace financial allocations. V92 remains the seller identity and Razorpay Route Linked Account layer. V94 will consume V93 allocations for creator balances and payout eligibility.

## Canonical flow
```text
Verified Razorpay payment
        ↓
Canonical commerceOrder
        ↓
product.creatorId
        ↓
creatorCommerceProfiles/{creatorId}
        ↓
Applicable commission rule
        ↓
Exact INR calculation
        ↓
commerceFinancialAllocations
        ↓
creatorRevenue projection
        ↓
Future V94 balance / Route transfer
```

## Commission rules
Rules live in `commerceCommissionRules` and are server controlled. Supported scopes are:

1. `product`
2. `creator`
3. `global`

Resolution is deterministic: product scope, then creator scope, then global scope; within the same scope, higher priority wins, then higher rule version, then the later effective timestamp.

Rules are versioned. Editing a rule creates a new immutable version for historical calculations. A future-effective version keeps the previous active version until the new effective timestamp.

Supported components:

- percentage, stored and calculated as basis points for exact arithmetic
- fixed INR amount
- optional minimum commission
- optional maximum commission
- `effectiveFrom` / `effectiveUntil`
- priority
- explicit zero commission

There is no hardcoded production commission percentage. A Master Admin must explicitly configure a rule.

## Exact money arithmetic
OFFSCRPT Commerce currently stores canonical product/order amounts in INR major units. V93 preserves those existing values and also stores authoritative financial subunits (paise) for calculation and reconciliation.

For a normal sale:

```text
creatorNet = gross - platformCommission
```

Invariant:

```text
grossAmountSubunits = platformCommissionAmountSubunits + creatorNetAmountSubunits
```

Commission percentage calculations and proportional refund reversals use exact integer arithmetic with `BigInt` to avoid floating-point rounding errors.

## Financial allocation
`commerceFinancialAllocations` is the canonical V93 financial allocation record. A normal sale uses a stable allocation ID derived from the OFFSCRPT order ID, so repeated payment callbacks/webhooks cannot create multiple sale allocations.

Each calculated allocation stores:

- order/payment/product/creator/seller identifiers
- Razorpay Linked Account ID when available
- gross amount and subunits
- OFFSCRPT commission and subunits
- creator net and subunits
- commission rule ID/version
- immutable calculation snapshot
- financial status
- future transfer status (`not_started` in V93)

`creatorRevenue` is updated as the creator-facing revenue projection and retains the V93 commission fields.

## Refund/reversal accounting
V93 consumes Razorpay refund webhook events but does not expose an automatic payout/refund button as part of the V93 scope.

Supported signed refund events include:

- `refund.created`
- `refund.processed`
- `refund.failed`
- `refund.reversed`
- `refund.speed_changed`

For `refund.processed`, OFFSCRPT verifies the provider refund and its payment linkage, records the canonical `commerceRefunds` document, and creates one deterministic `refund_reversal` financial allocation.

The configured default policy is proportional reversal of the original commission allocation. On a full cumulative refund, the remaining commission/creator amounts are reversed exactly so the original allocation is fully neutralized.

Refund invariants:

```text
cumulativeRefundedAmount <= originalGrossAmount
cumulativeCommissionReversed <= originalPlatformCommissionAmount
cumulativeCreatorReversed <= originalCreatorNetAmount
```

Historical orders/payments/revenue records are preserved.

## Financial states
V93 separates payment state from financial state. Financial allocations can be:

```text
pending
calculated
adjusted
reversed
partially_reversed
error
reconciliation_required
```

A paid order remains paid if commission calculation temporarily fails; its financial allocation is placed in `reconciliation_required` so support/admin can recover it without deleting the sale.

## Admin controls
Master Admin receives:

- Commission Rules management
- rule version history
- activate/deactivate controls
- commission simulator
- lightweight finance totals
- order financial lookup
- commission reconciliation for recoverable allocations

No admin screen can directly edit historical financial snapshots.

## Creator view
Creator Dashboard receives an `EARNINGS` tab showing server-calculated:

- Gross Sales
- OFFSCRPT Commission
- Creator Net
- Refunded amount
- Commission reversed
- Creator amount reversed

These are earnings metrics, not withdrawable balances. V94 owns balances and payout eligibility.

## Security
All V93 financial mutations remain server authoritative. Clients cannot directly write commission amounts, creator net, financial status, rule versions, or refund reversals through Firestore rules.

Financial attribution is derived from:

```text
order → product.creatorId → seller profile → razorpayAccountId
```

Client-supplied creator, seller, account, commission, or refund values are not trusted.

## Route compatibility
V93 records the Razorpay Linked Account ID as the future settlement target but does not execute `createTransfer` and never creates fake transfer IDs. V94 will decide when an allocation becomes withdrawable and when an actual Route transfer is initiated.

## V94 handoff
V93 creates financial allocations.
V94 creates creator balances and payout eligibility.

## V95 handoff
V95 will build advanced admin finance and revenue analytics.
